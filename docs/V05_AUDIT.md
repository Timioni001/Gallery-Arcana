# v0.5 implementation audit and limits

This is an engineering review with automated tests, not independent security certification. Real Zcash and production custody remain blocked. The complete protocol is CRYPTO_PROTOCOL.md; the full adversary model is THREAT_MODEL.md.

| Finding / risk | Implemented control and verification |
| --- | --- |
| A separate signing-key signature alone does not prove possession of an encryption key | Five-minute HPKE-encrypted random challenge; account/origin/fingerprint binding, new-key signature, old-key rotation signature and one-time completion. Wrong/missing continuity and replay are rejected. |
| Transaction timestamps can invert identity history under locks | Per-account revision counters under serialized account locks select current history, rather than creation timestamps. Integration tests invert stored timestamps and prove a revoked old key cannot authorize the next rotation. |
| Rotation/revocation can race envelope validation or create FK lock inversions | Transactional active-key shared locks; registration/reset use account NO KEY UPDATE locks compatible with FK KEY SHARE; conversation quota takes listing before account/key locks. No financial mutation retries an external wallet send. |
| Static ciphertexts can be tampered, reordered, truncated or routed to another resource | AES-GCM per-chunk count/index/header AAD; private metadata/digest verification; HPKE envelopes signed over origin/purpose/resource/nonce/accounts/key IDs; negative client/server tests reject tampering and wrong keys/pins. |
| Seller disappears after funding | Buyer key envelope must be prepared before checkout and is snapshotted. Historical authorized delivery does not depend on a fresh seller action or pre-checkout eligibility expiry. Dishonest prepositioned keys remain a dispute risk. |
| Premature buyer key retrieval | Account/receipt and locked funded/paid/disputed order gates; review/refund denies new delivery. DB-only storage tests find no client content/private keys or protected plaintext. Privileged out-of-band early release is outside this access-control guarantee. |
| Upload query/encoding variants bypass early authentication before large body parsing | Upload authorization uses Fastify matched route metadata, covering query strings and routed path variants; an unauthenticated capsule query with unsupported content type returns 401 before parsing. |
| Message injection, replay, membership bypass or hidden plaintext attachments | Signed dual-recipient copies, pinned roster, unique UUID/sequence, strict context/expiry and bounded attachment checks. Outsider, altered-signature, replay and expired-conversation tests fail. Financial amounts remain visible and legacy records are not relabelled encrypted. |
| Invitation identifier becomes a bearer secret in URLs | Separate opaque UUID/body-only 256-bit capability; only its hash persists. Recipient, revision, expiry, revocation and single checkout transaction are enforced. Invitation-only public metadata/offer/conversation/direct-checkout access is gated. Parallel redemption yields one order. |
| Full histories leak through reputation | Explicit audience-bound minimal passport issuance; source identifiers/counterparties/hash/amount omitted; counts opt-in. Public verification needs the proof, no certificate search feed. Holder nonce proof and signature/online revocation are separate operations. Stable holder fingerprints remain linkable. |
| Revoked/compromised keys or invalidated sales keep minting credentials | Issuer registry/history and revocation, identity reset/rotation revocation, conservative passport invalidation on payment review, and fail-closed current issuer readiness/release. Historical-key verification/revocation tests pass. Offline verification cannot check current revocation. |
| Operators automatically gain private dispute content | Participant-selected reviewer-bound HPKE packages and explicit disclosure; assigned reviewer session only. Admin token alone does not retrieve/decrypt evidence. Replacement needs new consent/key envelopes. Package hashes and append-only decision trigger support audit, not legal truth or DB-owner tamper immunity. |
| External control challenge becomes SSRF, signature replay or custody | DNS TXT only, validated fixed public GitHub raw path, no redirects, bounded network reads; EIP-191 library recovery with domain/account/subject/chain/nonce/expiry. Single-use transactional consumption and private observations. Synthetic DNS/GitHub observations are labelled, not claimed live. |
| New features weaken existing money/recovery behavior | Existing tests retained. Original server-encrypted journey, legacy mock demo, two-buyer checkout, receipt authorization, partial/excess/late refunds, lost-send reconciliation, review freezes and actual worker SIGKILL/lock-loss recovery remain in the full suite. |

## Remaining material risks

- No funded/synchronized real Zallet/Zebra environment exists; no live receive/payout/refund/reorganization or uncertain-send reconciliation has been verified. Current evidence is docs/evidence/zcash-testnet-v05.json.
- Initial directory trust needs out-of-band pins; no transparency log or independent first-contact identity authority is implemented.
- Client compromise/malicious delivered code, static-key historical compromise, recipient redistribution and loss of offline recovery material remain outside ciphertext-at-rest protection. Browser interoperability is not established by Node tests/DOM compilation.
- HPKE/AES/WebCrypto are standard primitives from maintained implementations; this specific composition, account policy and client distribution still need independent cryptographic/application review.
- Operator custody, shared administrative token, development DB identities, fixed FX, missing production key vault/backup restore/load/monitoring acceptance and proxy deployment controls remain production blockers.
- Purchased envelope routing is retained for old-key recovery; metadata and backups are not completely erased. Sender equivocation and submitted evidence truth are not cryptographically adjudicated.
- Passport signatures are platform statements; no ZK/unlinkability/legal title/independent onchain proof is claimed. Revocation relies on the online registry and a relying party must manage its own holder-challenge nonce lifecycle.
