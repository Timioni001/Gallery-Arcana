# v0.5 privacy and security threat model

This is a custodial marketplace with explicit client-encrypted modes, not trustless escrow. Real-wallet/mainnet/production modes remain disabled. The application and database enforce state/access rules; client cryptography limits what ordinary storage compromise reveals. Neither test success nor use of standard primitives is an independent protocol audit.

## What each party can see

| Party | Visible information / trust boundary |
| --- | --- |
| Public visitor / blockchain observer | Public listing metadata and chosen previews; no public buyer/order/offer feed, private invitation details, proof inventory or asset-control inventory. Unlisted URLs reveal metadata to URL holders except invitation-only listings, which require capability/owner access. Mock payments have no onchain privacy/finality. Future real shielded transfers must be verified separately. |
| Buyer and seller | Their own financial negotiations, relevant counterpart identity/key IDs, own invoices/receipts or seller summaries, and messages encrypted to them. Authorized capsule buyers receive the prepared key envelope after funding. A recipient can retain/share plaintext and keys. |
| API/operator | Account relationships, listing labels, amounts, timing, invoices, payout destinations, conversation membership and encryption-key routing. It can decrypt legacy originals and read legacy offers/reasons. It ordinarily holds no capsule content key, client private key, encrypted message plaintext or reviewer evidence plaintext. |
| Database/storage-only observer without client keys | Ciphertext, sizes, routing identities, financial records and ciphertext hashes. Even knowledge of the server's at-rest file key reveals only the inner capsule ciphertext. No claim conceals metadata or protects unencrypted legacy records from database access. |
| Assigned reviewer | Explicitly selected packages encrypted to their pinned key. No automatic product/conversation decryption. The shared admin token alone grants no evidence decryption. |
| Writable database owner / compromised API | Can alter policy/state, roll back revocations, substitute unpinned directory roots, deny service and release prepared envelopes prematurely. Existing pinned client keys still protect ciphertext authenticity/confidentiality, but this is not a cryptographically immutable custody/access-control system. |

## Client encryption and identity trust

Capsules use fresh random content keys and chunked AES-256-GCM with authenticated header/count/index, encrypted names/MIME/plaintext digest and final local digest verification. HPKE (RFC 9180, P-256/HKDF-SHA256/AES-256-GCM) delivers buyer-specific keys. ECDSA signatures bind origin, purpose, resource, message nonce, expiry and exact sender/recipient identities. Server registration requires account authorization, encrypted proof of encryption-key possession and the new signing key; rotations additionally require the old signing key. Monotonic revisions prevent timestamp-based continuity forks. Shared row locks serialize validation against key revocation.

First-contact fingerprints must be compared using an independent trusted channel or previously pinned trust. A self-signed key returned by a server is not independently authenticated against that server/database. Recovery resets require a fresh passphrase, revoke affected credentials and deliberately break continuity; clients must re-pin. Retain old keys and delivered envelopes for historical products. A reset without a backup does not recover old plaintext.

The SDK uses exportable private keys for encrypted offline recovery backups. A random 256-bit recovery key must be stored separately. Manual restoration on another device is supported using an encrypted file or authenticated account backup plus its separate recovery key. There is no live multi-device key synchronization, secure memory wiping, hardware-keystore integration, endpoint-malware protection or Signal-style forward secrecy. Later compromise of a static recipient private key can reveal retained historical envelopes. Malicious server-delivered client code/browser extensions can steal keys before encryption and are outside ordinary ciphertext-storage protection. Independently distributed/audited client code is needed for stronger operator resistance.

Prepositioned key envelopes prevent an honest seller disappearing after checkout from requiring another delivery action. A malicious seller can still prepare an incorrect key or dishonest product. Buyer verification/held proceeds and disputes handle failure; cryptography does not prove authenticity, licensing or fair exchange. A privileged early release to a buyer who owns the recipient key bypasses the funding gate. Once a key/file is released, later revocation/review cannot erase it.

## Conversations, evidence and attestations

Encrypted conversations protect participant text and bounded attachments. Backend offer/counter amounts and settlement-critical transitions remain plaintext operator-visible metadata. Both recipient copies are authenticated but equal plaintext between copies is not proven; a malicious sender can equivocate. New messages stop after rotation/revocation until a new pinned conversation is created. Expiration/deletion removes server copies, not recipient copies or backups.

Evidence disclosure is explicit and selected by a participant. Reviewer replacement requires fresh pinning and re-encryption by a participant; old evidence cannot be silently decrypted for the replacement. A signed package establishes its submitting key, not the truth of its contents or original counterparty authorship. Operators resolve disputes explicitly; a buyer confirmation is not a legal guarantee of satisfactory/authentic/licensed content. Decision rows reject application UPDATE/DELETE, but a privileged DB owner can alter triggers/backups. Shared-token actions lack individual operator attribution.

Trade Passports are minimal platform-signed historical claims. Fresh serials omit transaction IDs/hashes/counterparties; exact delivery counts are opt-in. Audience, expiry, key history and revocation are checked online. Offline signature verification does not check live revocation. A relying party must separately verify holder possession with its own fresh, expiring, consumed nonce. Stable holder fingerprints/repeated serials are linkable; this is not ZK disclosure or unlinkable reputation. Payment reviews conservatively revoke affected acquisition/seller credentials. Legacy v1 receipt proofs remain historical statements and have their original verification contract.

## Application attackers and custody failures

Tests exercise object-level authorization, CSRF, token rotation/revocation, seller ownership, stale revisions, duplicate messages/invites/payments, tampering, concurrent checkout/dispositions, storage traversal/symlinks, malformed previews and worker restart/lost-send recovery. Parameterized SQL, explicit response projections, unique constraints and transaction locks defend these boundaries. Key challenge/reset, message, invitation, asset-control and passport routes have additional limits; distributed Sybil/DoS attacks remain possible.

Session cookies are HttpOnly/Strict SameSite/Secure on HTTPS, with exact-origin/custom-header/fetch-site checks and no external CORS permission. Secrets, invoice memos, receipts, message bodies and wallet errors are not logged. Capability secrets belong in request bodies, never URLs/analytics. All `/api/admin/*` routes must be blocked at an external proxy: a proxy can make remote requests appear loopback. No individual operator RBAC/MFA or independent tamper-proof audit service exists.

An invoice is funded only by exact canonical output attribution at required confirmations; balance changes and buyer-supplied txids do not prove payment. Reorganizations freeze new delivery/spending and affected passports; uncertain sends are never blindly retried. Already sent funds/downloaded files cannot be undone. No automatic timeout release or payment-review bypass exists. Production still needs distinct API/worker OS/database identities, real-wallet verification, limits/monitoring, fresh FX and independently tested custody recovery.

## Retention and operational limits

Expired messages/conversations, pending challenges, evidence, unreferenced envelopes, invitations, passports and expired control observations are cleaned by the worker. Settled financial cleanup removes buyer/payment/offer links, dispute reasons and completed mock send details; unresolved funds remain recoverable. Purchased capsule envelope routing retains buyer/seller key/account IDs and listing association for authorized old-key recovery even after financial-link cleanup. This limits metadata erasure; do not claim complete transaction unlinking. Decision package hashes and public key history remain for audit/verification. Backups and real wallet history have separate retention constraints.

DNS/GitHub/EVM observations establish technical control at a point in time only. DNS trust depends on resolver/zone delegation; public GitHub file proof has no private-repository/organization role support. EIP-191 signing proves a key, not NFT ownership, contract-wallet authorization or onchain state. No automatic external transfer or cross-chain custody is provided.

Malware scanning, legal/rights moderation, real-browser interoperability, independent cryptography/application review, key vault/rotation recovery and encrypted backup restoration remain outstanding. See CRYPTO_PROTOCOL.md for exact formats/limits and ZALLET_GAP.md for the blocked live testnet gate.

## Account backup storage

Optional account backups add operator-visible backup timestamps, size and account linkage. Only AES-GCM ciphertext is uploaded; the server never receives the random 256-bit recovery key. Database-only access cannot decrypt a correctly created backup. The server can delete, withhold or replay a snapshot; revision checks prevent ordinary concurrent replacement, not privileged database rollback. Account/origin and active-key checks reject substituted or obsolete identities during restore. Lost login passphrases cannot be retrieved from hashes; lost recovery keys cannot be derived from the login credential. A compromised session can delete/replace an account backup, so retain an offline copy. Database backups may retain removed ciphertext under their separate retention policy. Manual restore does not restore trusted-peer pins; reverify fingerprints independently.
